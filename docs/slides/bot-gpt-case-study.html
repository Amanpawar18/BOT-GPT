Context Strategy: Sliding Window

Default — zero extra API calls. Always keeps the most recent context.

budget = 8 000 tokens (open) | 6 000 (RAG) messages = [msg₁ msg₂ msg₃ msg₄ msg₅] oldest ──────────────► newest walk newest → oldest: msg₅ 80 t total=80 ✓ add msg₄ 120 t total=200 ✓ add msg₃ 7400 t total=7600 ✓ add msg₂ 900 t total=8500 ✗ exceeds budget → stop window = [msg₃, msg₄, msg₅] ← chronological order Edge case: msg₅ alone > budget? → still include it (minimum-1 guarantee) → conversation continues, just no history

Why newest → oldest?

We want to guarantee the most recent turn is always present. Walking from oldest→newest would drop it under budget pressure.

Token estimation

Math.ceil(text.length / 4) — synchronous, zero latency. Stored on each message at save time.

Budget split

RAG uses 6k (not 8k) to leave headroom for the retrieved chunk context block injected into the final message.

Context Strategy: Summarization

For long conversations — preserves semantic content of old turns at the cost of one extra LLM call.

Step 1 first-pass window firstPass = buildContextWindow(messages, budget=8000) older = messages before firstPass → [msg₁ … msg₉₄] Step 2 summarize older slice (1 LLM call) summary = await aiService.summarizeHistory(older) summaryTokens = estimateTokens(summary) // e.g. 350 Step 3 rebuild recent window accounting for summary recent = buildContextWindow(messages, 8000 - 350) ← summary tokens reserved so total never overruns budget Step 4 final context to Gemini: [ SystemMessage("You are BOT GPT…"), AssistantMessage("[Earlier conversation summary]: …"), …recent messages…, HumanMessage(current query) ]

Bug fixed this session: original code built recent window at full budget, then prepended summary — could silently exceed the budget. Fixed by deducting summary tokens before the second buildContextWindow call.

Why Cloudflare R2?

S3-compatible API — zero egress fees vs AWS S3. Raw file stored for potential re-processing. Public URL returned and saved in documents.r2_url.

Daily Token Limit

Hard cap of 100 000 tokens / user / UTC day — enforced before any LLM call or SSE headers.

getDailyTokensUsed(userId): SELECT COALESCE(SUM(msg.token_count),0) FROM messages msg JOIN conversations conv ON conv.id = msg.conversation_id WHERE conv.user_id = :userId AND msg.created_at >= :startOfUTCDay sendMessage(): const dailyUsed = await getDailyTokensUsed(...) if (dailyUsed >= 100_000) { return res.status(429).json({ error: "Daily limit of 100,000 tokens reached. Resets at midnight UTC." }) ← plain JSON, not an SSE event } // proceed: set SSE headers, stream… After stream completes: saveMessage(id, 'user', content, userTokens) saveMessage(id, 'assistant', full, assistantTokens) convRepo.increment(id, 'token_count', total)

Why before SSE headers?

Once Content-Type: text/event-stream is written, the response is locked — you can only write SSE events, not switch to a JSON error body. The limit check must happen first.

Resets at UTC midnight

startOfDay.setUTCHours(0,0,0,0) — consistent boundary regardless of user timezone.

Configured via env

DAILY_TOKEN_LIMIT=100000 — defaults to 100k if not set. Adjustable per environment.

LLM Retry: Exponential Backoff

private async withRetry<T>(
  fn: () => Promise<T>,
  maxAttempts = 3,
): Promise<T> {
  let delay = 1000;
  let lastError: unknown;
  for (let i = 1; i <= maxAttempts; i++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      if (i < maxAttempts) {
        await sleep(delay);
        delay *= 2;      // 1s → 2s → 4s
      }
    }
  }
  throw lastError;   // bubble up after 3 fails
}

// Usage:
const stream = await this.withRetry(
  () => this.llm.stream(messages)
);
Attempt 1 ──► Gemini 503 error sleep 1 000 ms Attempt 2 ──► Gemini 503 error sleep 2 000 ms Attempt 3 ──► Gemini 200 OK → tokens stream If all 3 fail: SSE handler catches error res.write(`{"error":"LLM unavailable"}`) res.end()

Tested with Jest

Mock setTimeout to run instantly, make llm.stream fail twice then succeed. Assert tokens arrive on attempt 3 and mockStream called exactly 3 times.

NestJS CacheModule config (app.module.ts): CacheModule.register({ isGlobal: true, ttl: 60_000 // 60 seconds }) @Inject(CACHE_MANAGER) private cache: Cache

Why in-memory, not Redis?

Single instance deployment. NestJS CacheModule (node-cache internally) adds zero infrastructure. Redis is the right call when running multiple API instances that need a shared cache.

What's cached

Only GET /conversations — the highest-frequency read. Single conversation fetches (GET /conversations/:id) are not cached since they include the full message list and change with every send.

Switching to Redis later

Replace CacheModule.register() with CacheModule.registerAsync() + @nestjs/cache-manager Redis store. Zero changes to service code.

Where it Breaks at Scale

Users ──► API layer ← stateless, scales horizontally behind any LB │ ▼ PostgreSQL ← single writer, ~10k concurrent writes before it struggles │ ▼ Gemini API rate limits ← shared quota across all users

DB bottleneck

Read replicas for GET /conversations + message history.

PgBouncer for connection pooling.

Partition doc_embeddings by conversation_id.

Shard messages by conversation_id at extreme scale.

LLM cost

Redis cache for repeated RAG queries (same question + same docs = same answer).

BullMQ queue for document embedding — async, retryable, off the request path.

Caching

Swap in-memory CacheModule for Redis store.
